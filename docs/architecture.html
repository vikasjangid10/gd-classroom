A voice-first group discussion, moderated by an AI

A host picks four people registered on the app; the invitation lands in their session over their own event stream, with no reload and no email. One topic, one AI moderator that holds the floor and hands it out fairly. Audio never leaves the real-time plane; business facts never leave PostgreSQL; conversation state lives only in the process that is running the session, and dies with it.

Part I · Architecture

How the system is cut into pieces, and what moves between them.

01High-level architecture

One deployable process. Three transports, each with exactly one job. Nothing between the app and PostgreSQL.

The whole system is a single FastAPI application. That is a deliberate choice, not a shortcut: a group discussion is a tightly coupled real-time interaction where the moderator's next decision depends on audio that arrived 200 ms ago. Splitting the orchestrator, the STT consumer and the turn policy across service boundaries would add network hops to the critical path of every single turn, and would force the ephemeral session state into a shared store — the one thing the brief rules out.

Instead the boundaries are drawn inside the process, as modules with explicit interfaces. Each module owns its tables, exposes a service facade, and never reaches into another module's repository.

What is deliberately absent

no Redisno Kafkano RabbitMQ no vector DBno Elasticsearchno microservices no long-term memory

Every one of those is normally introduced to solve a problem this system does not have. There is no cross-node fan-out (a session lives on one node), no durable job queue (there are no background jobs that may not be lost), no retrieval (the LLM's entire world is one discussion), and no full-text search (transcripts are read by session_id, never searched). PostgreSQL covers persistence, LISTEN/NOTIFY covers the one cross-node signal we may eventually need, and Python's asyncio covers concurrency.

03Request flow diagrams

Three planes with different latency budgets, different failure modes, and different reconnection semantics.

Plane invariants

  • REST never pushes. A mutation returns the new resource and nothing else. Any consequence other clients must learn about is published as a domain event after the transaction commits, and reaches them over SSE.
  • SSE never mutates. The event endpoint is a pure read. A client that wants to act does a REST call; it then learns the outcome twice — once as the HTTP response, once as an event — and the reducer is written to be idempotent so this is harmless.
  • WebRTC carries no application data. No data channel, no JSON over RTP. Signalling is REST (POST /rtc/offer), state is SSE, media is media. This keeps the media plane restartable without losing a single piece of application state.

05AI orchestration lifecycle

One session, one asyncio task, one queue. Every input — a finished utterance, a timer, a participant dropping — becomes a command, and commands are processed strictly one at a time.

This is the single most important structural decision in the system. A live discussion has at least six concurrent event sources (four audio streams, provider callbacks, wall-clock timers, REST commands from the super user). Handling them with callbacks and locks produces races that only appear under real network conditions. Instead every source is a producer that puts a command on a queue, and a single consumer task owns all mutable session state. No lock is ever taken, because there is only one writer.

The turn cycle

Inside DISCUSSION, one turn is:

1. SELECT   TurnPolicy.next_speaker(ledger, last_speaker, coverage)
             → participant with the least floor time, excluding the
               previous speaker unless they are the only one left

2. ASK      PromptBuilder.question(topic, rolling_summary, recent_turns,
                                    target=participant, turn_index)
             → LLM streams a question → TTS → AI track
             → event: moderator.question  { speaker_id, text }

3. YIELD    grant_floor(participant)
             → server unmutes only that participant's relayed track
             → event: floor.granted  { participant_id, max_seconds: 90 }

4. LISTEN   STT partials → event: transcript.partial (throttled 4/s)
             ends on: utterance_final (1.2 s silence)  |  hard cap 90 s
                      |  participant releases floor  |  disconnect

5. JUDGE    FollowUpPolicy.decide(answer, turn, ledger)
             follow up when: answer < 25 words  ·  a claim went unsupported
                             ·  this participant is still under quota
             at most one follow-up per participant per topic thread

6. ADVANCE  ledger.add(participant, spoken_ms); summarise if context
             is over budget; back to step 1 — or to CLOSING if the
             time budget is spent and everyone has met the floor

Context budget — rolling summary

The LLM sees a fixed-size window regardless of how long the discussion runs. After every turn the runner estimates tokens; when the verbatim tail exceeds its budget, the oldest turns are folded into a running paragraph by a cheap model call, and dropped.

# domain/moderation/context.py

TOPIC BRIEF     ~200 tok   topic title, description, 4 guiding angles

                             problem; Arjun challenged chunk sizing…"

                             ─────────
                             ≤ 2.2k tokens, flat, forever
Because the window is flat, turn latency does not degrade as the discussion grows, and the cost of a 45-minute session is linear in turns rather than quadratic. This is the whole reason a rolling summary is preferred over simply sending the full transcript.

Hearing the host without a microphone

WebRTC is the right transport for a conversation — low latency, and it carries the participant's own voice back. But joining it requires a microphone, and plenty of people open a discussion on a laptop that has none, or has not been granted permission. The first version simply skipped synthesis when nobody was on the media plane, on the reasoning that synthesising into an empty room wastes the event loop.

That reasoning was wrong, and the symptom was damning: those people got a silent host and a caption racing past — the entire discussion scrolled by in a few seconds. Two separate defects, both from the same cause. There was no audio, and because the runner paces itself by asking the mixer whether its buffer has drained, an empty mixer meant "the host has finished speaking" the instant it started. A group discussion nobody can hear, running at four times speed.

Every moderator sentence is now synthesised once and delivered twice: into the mixer for WebRTC listeners, and as a SpeechClip that any browser can fetch over ordinary HTTP and play. Both hear identical audio, because it is the same PCM — the clip is not a second rendering. And wait_until_silent() now watches two clocks, the mixer backlog and the duration of what was synthesised, so the host is paced by the length of its own speech whether or not anyone is on the media plane.

And a second, worse one on the WebRTC side — synthesis is not a live source. The mixer gives each peer a read cursor and skips it to the live edge whenever it falls more than a second behind. For a microphone that is exactly right: audio arrives at one second per second, so a peer a second behind is genuinely lagging and you want the conversation as it is happening rather than a growing delay. Synthesised speech does not behave that way at all. Piper produces a five-second sentence in about one second, and it lands in the buffer all at once — while the peer can only ever consume 20 ms per frame in real time. Measured by the same rule, every listener was instantly four seconds "behind", so the mixer skipped each sentence to its final frame. A participant on a microphone heard 20 milliseconds of every sentence the host spoke — in practice, the word "begin" and nothing else. Measured against a real aiortc peer: 1 of 150 frames before the fix, 150 of 150 after, and 32.8 seconds of audible speech across a real discussion. The lag rule now applies to the microphone buffer only; the moderator's is a queue to be played in full.

The moderator may not put words in anyone's mouth

The context block used to hand the model one interleaved transcript — moderator turns and participant turns together, each rendered as Name: text. In a room where everybody was present but nobody actually spoke, that produced the worst failure this system has had:

It read its own question back as somebody's contribution. The moderator asked "Arjun, how do you see this protocol impacting tool discovery and capability negotiation?", got silence, and opened the next turn with "Arjun highlighted the significance of tool discovery and capability negotiation." Arjun had not said a word. The transcript panel showed a dozen such lines: an entire discussion attributed to four people who were sitting there in silence. Nothing in the scripted provider could ever have shown this — a fake moderator has no opinions to invent.

Three changes, in order of how much they matter:

  1. The prompt separates what was said from what was asked. Contributions are listed under "the ONLY things you may attribute to anyone"; the moderator's own recent lines are listed separately and labelled as its own. When there are no contributions, the block says so in words — NOBODY HAS SAID ANYTHING YET — rather than leaving an empty section for the model to fill.
  2. The persona leads with it. "Never put words in anyone's mouth… Your own earlier questions are NOT contributions." It is the first rule, above the voice rules, because it is the one that matters.
  3. Silence is counted, and the discussion gives up. Turns that come back empty increment consecutive_silent_turns; at MAX_SILENT_TURNS the session closes as NOBODY_SPOKE and the closing prompt is told to say the discussion could not get going instead of inventing conclusions.
The third one is the structural fix and the other two are guardrails, which is the right way round. A moderator questioning an empty room indefinitely will eventually manufacture something to talk about, no matter how the prompt is worded — the answer is to stop asking. Counting silence also fixed a fairness bug hiding underneath it: a participant who never speaks keeps the least speaking time, so the round-robin kept handing the floor back to the same silent person. A timed-out turn now spends that person's turn.

Two different clocks, and the one that was actually enforced

Handing over the floor arms two timers, and conflating them made the moderator feel as though it were pushing everyone through a queue:

TimerQuestion it answersDefault
capHow long may a turn run once it is under way?TURN_MAX_SECONDS — 90 s, and the number the host says out loud
silenceHow long does somebody have to begin?SILENCE_BEFORE_SPEAKING_SECONDS — 25 s
The silence window was a hardcoded twelve seconds, and losing it cost you your whole turn. So the moderator would promise ninety seconds, hand over the floor, and — while the participant was still drawing breath, or finding the unmute button — nudge once and call on somebody else. The number it announced was never the number being enforced. Worse, that lost turn counted as silence, so a room of people all taking a moment to think would be closed for not talking. Reported exactly as it felt: "jaise ye jaldi jaldi kaam khatam karne me laga hai".

A slow start is now handled the way a person would handle it. Twenty-five seconds to begin; if nothing comes, the host asks whether they are still there and hands the floor straight back for another fifteen; only if that also passes is the turn spent and the rotation moved on. Roughly forty seconds and an explicit check before anybody loses their place — and speaking at any point, including over the check itself, cancels the whole thing. Measured against the live model with participants who deliberately waited eighteen seconds: three late answers, three recorded on their own turns, zero interruptions.

Nobody is named in the round

A group discussion is judged on what people say, and the name on an account carries region, religion, community and family — every one of them a thing a listener can be swayed by without meaning to be, model or human. So the account name never enters the room. Each seat is given a different name for that discussion — Harsh, Leher, Pooja, Zaid — and that is the only name the other participants, the live transcript, the stored transcript, the summary and the moderator ever see.

Names rather than "Speaker 1". The first version numbered people, and it was wrong in a way that only showed once it was running: a moderator saying "Speaker 3, what do you think?" sounds like a ticketing system, and a room of numbered seats stops sounding like a discussion at all. A name does exactly the same anonymity work while leaving the room human — which is the whole point of the product.
Gender is declared, never guessed. For the name to fit the person it has to come from the person, so it is a field they set at sign-up and may leave blank. It is emphatically not inferred from their real name: name-to-gender guessing is wrong often enough to matter, and it is wrong most often for the least common names — the worst distribution a mistake could have, and it would hand somebody a name contradicting who they are inside a room built to protect them. A seat that declared nothing draws from the whole pool, which is a first-class outcome and not a degraded one. The gateway fetches gender and not the name it belongs to: UserService.genders() exists precisely so that the discussion can be given what it needs without being given what it must never have.
Structural, not a matter of prompt hygiene. SessionDataGateway.load_live_session is the single place a live discussion is populated, and it no longer looks the real names up at all — it derives call-signs from the roster instead. A name that is never put into the context cannot be repeated out of it. The same substitution is applied at the two read endpoints, so a transcript read afterwards says exactly what was on screen at the time.

Contact details are a removal, on the spot

A group discussion is a room of strangers, and its transcript is captioned live to every screen, summarised by a model, and written to Postgres. An email address or phone number said out loud in that setting is almost never part of the discussion. Anyone who reads one out is taken out of the round immediately, and — the part that matters more — the words themselves are dropped rather than stored.

Persisting the number while punishing the person who said it would be the whole failure. So the utterance is never recorded as a turn, never enters the moderator's rolling context, and never appears in an event payload; only the kind of detail (["phone"]) travels. The live caption is redacted at source too, because interim transcripts are published several seconds before the final one that triggers the removal — untouched, the number would already be on four screens by the time anyone was removed for saying it. The announcement is a fixed string for the same reason the ground rules are: a model asked to explain why somebody was removed for reading out a phone number will, given the chance, read out the phone number.
Rules, not a model

app/domain/privacy.py is pure regex, and deliberately so. A detector that catches four numbers in five is worse than none at all, because it teaches people the room is safe when it is not. These patterns are deterministic, run in microseconds, cost nothing per turn, and every one is a test case. A model asked "does this contain personal information?" is slower, adds a request in the middle of a turn, and is wrong in both directions — it will find a phone number in "ninety seconds" and wave through one it has decided is fictional.

The second rule exists because the first one missed. The threshold started at ten digits, on the reasoning that a mobile number is ten. Then somebody said "My file number is 63771346" in a real discussion and stayed in the room: eight digits, not a phone number, unmistakably personal. Two changes followed. The bare-digit threshold dropped to eight — a landline is eight, and no measurement in a technical discussion is (figures spoken aloud are five digits or fewer, and larger ones are said in words). And a second rule was added for the case length cannot decide: when the sentence has already said whose number it is, four digits is enough. The framing is the signal, not the length.

Postal addresses, employers and full names are not detected. They have no reliable shape, and a detector that guessed at them would eject people for saying where they work. Contact details are both dangerous and unambiguous, which is exactly the set worth enforcing — the honest limit is stated rather than papered over.

Removal is final for the round. The seat moves to REMOVED, the peer connection is closed, and both mark_connected and mark_disconnected refuse to move it again — otherwise the sanction would last exactly as long as it takes to press reload. That guard exists because a test caught its absence: the first implementation removed the participant correctly and then let them straight back in on the next ParticipantConnected. If the removal drops the room below two people, the host explains what happened before the session closes, so the person still there is not simply left alone. REMOVE_ON_PERSONAL_INFORMATION=false keeps the redaction and drops the ejection.

Deciding when somebody has finished talking

Groq serves Whisper as a file endpoint, so nothing tells this system where an utterance ends — groq_stt.py has to decide from the audio, and SILENCE_END_MS of quiet is what it uses. That threshold was 1200 ms, which is a reasonable number for dictation and a badly wrong one for a discussion.

A person thinking aloud pauses for longer than a second, constantly. So somebody would begin answering, stop to find the next clause — and the recogniser would declare the utterance over, the runner would treat that as their completed answer, and the floor would move on. From the participant's side the moderator had simply stopped listening halfway through their first sentence. Worse, when the fragment was too short to transcribe, the final came back empty, and an empty answer was taken as "they had nothing to say": turn spent, counted toward NOBODY_SPOKE.

Two changes. SILENCE_END_MS is now 2800, and an unforced empty transcript no longer ends a turn — UtteranceFinal carries a forced flag, set only when the moderator actually asked for the answer (the turn cap expired, or the speaker pressed "I'm done"). An empty final that nobody asked for means the recogniser had nothing usable yet, which is not a decision to stop talking: the floor stays put and the listening window is re-armed.

How this was finally caught. Every earlier test joined in text mode, which never touches WebRTC or speech recognition — the exact path the complaint was about. The test that found it publishes a real peer connection and speaks a real answer through it, synthesised with Piper, deliberately broken by a two-second pause in the middle. Before: one half recorded, the rest lost. After: both halves arrive as a single contribution and the moderator answers what was actually said. A pipeline that is only ever exercised by its bypass is not exercised at all.
And a deployment trap worth stating plainly: raising the default in config.py changed nothing, because .env pinned the old value — and docker compose restart does not re-read env_file, so even after fixing .env the container kept the old number until it was recreated. Two silent no-ops in a row, either of which looks exactly like "the fix did not work".

The beat before the reply

The host used to answer the instant a final transcript landed. That single detail is what made it read as a machine executing a script rather than somebody who had been listening. There is now a deliberate pause — MODERATOR_THINK_SECONDS, default 1.4 — published as moderator.thinking so the room shows considering what was just said rather than appearing to have frozen. It buys something concrete too: a late final transcript, or a participant who pauses mid-thought and carries on, both arrive inside that window.

The moderator runs on two chains, not on a provider

Because it does two different jobs, and they want opposite things from a model. The fast chain (LLM_CHAIN_FAST) writes what the room hears — questions, hand-offs, nudges — where a plain instruct model beats a clever one and every second is dead air. The deep chain (LLM_CHAIN_DEEP) judges what a participant actually said and writes the closing report, where reasoning is the point and nothing it produces is ever spoken aloud.

Every hosted provider appears in both under two names — gemini and gemini-strong — running two different models from one key. Rung names are per lane, and so are their ledger rows. That is not cosmetic: providers count a free-tier quota per model, so one shared row would bench a healthy rung the moment its sibling ran out — a failure that looks exactly like the feature working. The lanes also lead with different providers, so one bad day upstream cannot take out both jobs at once.

One ledger file, one event buffer, two chains. The rows cannot collide, and sharing is what keeps "gemini-strong went down four seconds after gemini did" a single readable sequence rather than two files somebody has to interleave by hand. Each event carries its own lane. The one thing that had to become per-lane is which rung served last: a single value had the two chains overwrite each other, and the status page showed one ACTIVE row across both — the lane that had just answered looking like the lane that had never run.
Judging an answer without making the room wait

The deep lane returns a small verdict on each contribution — substance 0-5, whether it engaged with what came before, whether a follow-up would add something, and one clause for the report. That verdict decides the last question in turn_policy.py: is this worth coming back to? It never decides the ones above it — out of follow-ups, out of time — because those are rules about the round rather than opinions about the words, and a model that can overrule fairness turns a good assessment into an unfair discussion.

It is bounded twice — the deep chain's per-rung ceilings, and a hard deadline at the call site — and every failure path returns None rather than raising, because the fallback is the word-count heuristic that was there before. The model is an improvement on that heuristic, never a dependency of it: a room must not fall silent because a judge was slow. Measured on a real discussion, the judgement costs 461-776 ms.

LLM_CHAIN is an ordered list of tiers. Every call walks it top-down, takes the first eligible rung, and moves down on failure. The chain is the retry — no provider is attempted twice within one call, because a retry against a provider that just refused is the most expensive possible way to discover it is still refusing, and it happens while four people are waiting to be spoken to.

The shipped order is gemini,groq,huggingface,openai,scripted: the free rungs first, the metered one as the last hosted resort, and a rung with no quota and no network in front of it underneath all of them. The four hosted tiers all speak OpenAI's chat-completions wire format, so each is a TierSpec and no adapter at all — which is the whole return on writing the client against the protocol rather than a vendor SDK. A rung with no key stays in the chain marked UNAVAILABLE, naming the variable it wants: dropping it silently would make "no key configured" and "healthy but never needed" identical on the status page, which is exactly the question somebody opens it to answer.

A reasoning model cannot serve this rung, and says so with a 200. The moderator writes one sentence and gets 220 tokens for it. A reasoning model spends that budget thinking and returns content: "" with finish_reason: length — a success, as far as HTTP is concerned. Measured on the real prompt: openai/gpt-oss-20b spent 218 of its 220 tokens reasoning and answered with nothing; gemini-3.7-flash took 44 s to produce four words. Both would have been a moderator who takes their turn in silence, scored by the ledger as a healthy rung that never needs replacing. The fix is in two places — GEMINI_MODEL is a lite model and reasoning_effort rides on every Groq call as a TierSpec.extra_body, and underneath them an empty answer raises, in complete(), in complete_structured(), and for a stream that ends without a token. A rung that says nothing must fail loudly enough for the next rung to be tried.
Only a spent quota moves the chain down for good. A throttle costs one call and a blip costs three before it costs anything; in both cases the top rung is first in line again immediately. That is the whole difference between a chain that prefers a provider and one that drifts down to its cheapest rung and stays there.

TRANSIENTafter 3 in a row, doubling to a capOne blip is not an outage. A fixed cooldown is wrong at both ends: short enough to re-probe a dead provider forever, or long enough to keep a ten-second blip benched for an hour. Any success resets the streak instantly.
Telling a daily quota from a throttle is the expensive decision, in both directions. Call a daily quota a throttle and the dead tier goes back to the top of the chain on the very next call, paying a full timeout to rediscover it, forever. Call a throttle a daily quota and a tier that would have been healthy in forty seconds sits out until midnight. No provider marks the difference machine-readably. Gemini sharpens it: its per-minute and per-day 429s carry the same sentence — "You exceeded your current quota" — and differ only in the quota id attached (…PerDayPerProjectPerModel versus …PerMinute…). So: a named window first ("per day", the quota id), then generic exhaustion wording (insufficient_quota, HTTP 402) but only when nothing in the body names a per-minute window, and then the retry-after duration as the signal — parsed from headers, from structured fields, and from prose, because Groq states it as "Please try again in 44m44.448s" and that sentence is the most useful thing in the whole error. Over five minutes is a day; under is a moment.
Caught in the wild, and worth the whole heuristic. Gemini's free tier for gemini-3.5-flash is 20 requests per day — and the 429 it sends says "Please retry in 32.394904523s", with retryDelay: "32s" in the structured details. Read by the duration rule alone, that is a thirty-second throttle: the spent rung goes straight back to the top of the chain and pays a round trip to rediscover the same 429 on every call until midnight. What catches it is the quota id sitting in the same body — GenerateRequestsPerDayPerProjectPerModel-FreeTier. A named window beats a stated duration, always, and the duration is only the signal of last resort.
Classification is on text, not on exception type. The same 429 arrives as httpx.HTTPStatusError from one adapter and a vendor-specific class from another; matching on types would need a branch per SDK, which is exactly the leakage this package exists to prevent. Every string a provider might have put the reason in — str(exc), .message, .body, .response.text, the retry-after header — is gathered into one lowercased blob and matched once. The detail is then truncated to 300 characters, because provider bodies run to kilobytes and every one of them ends up in a log line.
Things the walk has to get right
  • Ceilings are per tier. One global value either aborts a local model before it has finished loading or lets a hosted stall run for minutes.
  • Per-rung ceilings do not bound their sum, and the sum is what the person waiting experiences. Once LLM_FAILOVER_BUDGET_SECONDS has been spent hunting for a working hosted provider, the remaining hosted rungs are skipped and the local one is taken.
  • Skipping an ineligible rung costs zero network calls — that is the entire purpose of the ledger.
  • SDK and transport retries are off. They back off inside the router's hard timeout, so the chain never gets to try the next rung and collapses into one provider retried until the ceiling. Measured on a bad link: httpx with retries=5 turned a p50 of 400 ms into 100 seconds.
  • Streaming fails over only until the first token. After a chunk has been handed to the caller there is no way to splice a second provider's continuation onto the first one's sentence, so a later failure is re-raised rather than papered over with a different voice mid-sentence.
  • A structured-output parse failure is not a routing failure. The rung answered; it just answered badly. Benching a healthy provider over one malformed JSON body takes the best model out of rotation for something a single retry fixes.
  • Exhaustion subclasses TimeoutError. Every call site here already treats a slow model as a timeout; a brand-new exception type would mean auditing all of them, and one miss turns a quota event into a crash.
A tier that cannot work stays in the chain. No key, or a package that is not installed, marks it available=False with a reason a person can read, and it is skipped. Dropping it silently would make "no key configured" and "healthy but never needed" look identical on the status page — which is the exact question somebody opens that page to answer. For the same reason the page shows both active (the rung that served last) and next up (the rung that would serve now): they differ for precisely as long as it takes someone to notice a degradation and go looking.

What the model is not asked to write

The moderator has six kinds of utterance. Five need judgement — which angle to open, who to bring in, whether an answer was thin, how to close. One does not: the ground rules are the same four facts in the same order every session, varying only in the turn length. That one is a constant in app/domain/prompts.py and is spoken directly, with no model call at all.

This was learned from a real model, and only from a real model. The scripted provider had authored the rules turn perfectly for months. The first live gpt-4o-mini run said: "I will start with the first speaker, Alex." There is no Alex. Anything shaped like a hand-off makes a model produce a name, and the rules prompt had no roster to draw one from. Putting the four real names in the prompt made it worse — it then confidently handed the floor to whoever was listed first, one turn early, and asked the first question itself. Three prompt revisions in, the honest conclusion was that the prompt was not the bug: content that never varies should not be generated. Deleting the call removed the hallucination, one request per discussion, and about a second of latency before the first question.
A second live-only defect: the speaker label. The moderator is shown the transcript as Name: text, and a real model imitates that format in its own reply — "Moderator: Arjun made a good point." A speech synthesiser will happily say the word "Moderator" out loud to four people. The persona now forbids it, but a prompt is a request rather than a guarantee, so _strip_speaker_label() removes a leading label from the first sentence of every utterance before it reaches TTS. Only the first: a later sentence that happens to contain the word must survive untouched.

06Voice pipeline

Microphone to microphone in about a second, with cancellation available at every stage.

Why the server terminates WebRTC instead of meshing the peers

A four-way mesh would be cheaper on the server — and useless. The server must have the raw audio of whoever is speaking, because the moderator's decisions are made from it, and it must be able to publish a track of its own, because the moderator has a voice. So every browser opens exactly one RTCPeerConnection, to us.

That normally means running an SFU or a mixer. Here it means almost nothing, because the turn-taking rule guarantees at most one human speaker at a time. There is nothing to mix. The voice plane relays the floor-holder's track to the other three and drops the rest:

# infrastructure/voice/plane.py — the entire routing policy
def on_floor_change(self, holder: UserId | None) -> None:
    for pid, peer in self._peers.items():
        # each peer hears: the moderator, always; the floor-holder, if it isn't them
        peer.human_sender.replaceTrack(
            None if holder is None or holder == pid
            else self._relay.subscribe(self._peers[holder].inbound)
        )
        # STT is only consumed for the holder — three fewer provider sockets, three fewer bills
    self._stt.set_active(holder)

07SSE event flow

Every piece of shared truth reaches the browser as a numbered, replayable event on one stream per session.

A participant's screen shows who holds the floor, a live caption, the speaking-time bars and the roster. None of that is polled. There is exactly one EventSource per open room, and one per super user watching their classroom, and the reducer that consumes it is the single source of truth for the client's view of the room.

Wire format
id: 1042
event: floor.granted
data: {"v":1,"session_id":"01J8Z…","seq":1042,"ts":"2026-08-26T09:14:02.113Z",

The seq is monotonic per session and doubles as the SSE id, so Last-Event-ID replay is exact rather than approximate (§21). v is the envelope version; the client refuses events with a major version it does not know and prompts a reload.

Delivery guarantees
  • At-least-once, ordered per session. Reconnect replays from Last-Event-ID; a client may therefore see an event twice. Every reducer is idempotent — events carry absolute state (seconds: 41), never deltas (seconds += 3).
  • Slow consumers are dropped, not buffered. Each subscriber queue holds 100 events. On overflow the connection is closed with error: stream_overrun; the client reconnects and replays. Backpressure never reaches the orchestrator, which must not block on a stalled laptop.
  • Heartbeat every 15 s as an SSE comment, which keeps proxies and mobile radios from silently killing an idle stream.

Why EnrollmentService exists

Accepting an invitation is not an invitation-module operation. It marks an invitation, seats a participant in a classroom, may move the classroom to READY, and may provision a session — four modules. If InvitationService did that itself it would need ClassroomService and SessionService, and ClassroomService already needs InvitationService to send invitations. That is a cycle.

Rules a service follows

  • No commit. A service calls flush() when it needs an identity. The unit of work decides when the transaction becomes durable.
  • No HTTP. A service raises AppError subclasses. It never imports fastapi, and never knows a status code.
  • Events are collected, not published. uow.collect(event) queues; the dependency publishes after commit. A rolled-back transaction cannot leave a client believing something that never happened.
  • Constructor injection only. Every collaborator is a keyword argument, which is what makes the fakes in the test suite a one-line substitution.

14Dependency injection

Three layers of dependency, resolved per request, readable off the endpoint signature.

# app/api/deps.py — the seam between the request and everything else
async def unit_of_work(db: Db, bus: Bus) -> AsyncIterator[UnitOfWork]:
    """One transaction per request; domain events published only after it commits."""
    uow = UnitOfWork(db)
    try:
        yield uow
        await uow.commit()
    except Exception:
        await uow.rollback()
        raise
    else:
        bus.publish_all(uow.drain_events())

The one rule that needed two modules

"Who may watch a discussion?" is answered by the four participants and the host who convened them. Neither the session module nor the classroom module owns that question, so it is composed in the API layer where both services are already available:

# app/api/v1/sessions.py
async def _viewer(session_id, user, sessions: Sessions, classrooms: Classrooms) -> bool:
    """Returns True for the host. Composed here because neither module owns the other."""
    record    = await sessions.get(session_id)
    classroom = await classrooms.get(record.classroom_id)
    if classroom.created_by == user.id:
        return True
    await sessions.assert_member(session_id, user.id)   # raises 403 otherwise
    return False
This gap was found by driving the UI, not by reading the code. The host could create a classroom, match four people and watch it go live — and then had no way to open the room or end the discussion, because membership was defined as "has a seat" and the host has no seat. The endpoint returned a correct 403 to a button the interface should never have shown them. The fix was both halves: widen viewership to include the host, and return is_host in the session payload so the room offers each person only the controls that are actually theirs.
Floor control is authorization too

The most security-relevant decision in the whole product is not in the HTTP layer at all. Muting a microphone in the browser is a UI hint; a modified client can ignore it. So the floor is enforced on the server: a participant's inbound audio is dropped and their transcription socket is not even open unless the moderator has granted them the floor. There is no client-supplied claim in that path to forge.

Two bugs worth writing down

Both were found by running the application rather than reading it, and both produced the same symptom — a request that never returned, which is strictly worse than one that fails.

1. The handler that never ran. A registered @app.exception_handler(Exception) did not fire under uvicorn, so an unhandled error produced no response at all and the client hung until it timed out. The fix was to stop relying on framework internals for the last line of defence: RequestContextMiddleware is plain ASGI, wraps the downstream app in try/except, and — if the response has not started — writes the error envelope itself. A framework upgrade can now change a lot of things, but it cannot make a request hang.
2. The logger that took 75 seconds. With the catch-all in place, the request still hung — for exactly 75.8 seconds. A stack dump of the running process showed the event loop parked inside structlog's default pretty exception formatter, which renders every frame's local variables; on a deep ASGI stack that is pathologically slow, and it blocked the whole loop, not just that request. One line fixed it: ConsoleRenderer(exception_formatter=structlog.dev.plain_traceback). Unhandled errors now answer in 240 ms.

The second one is the more instructive. Nothing about it would have appeared in a code review, a type check or a unit test; it needed a real process, a real exception and a profiler. It is also the reason §32 specifies plain tracebacks as a requirement rather than a preference.

21Reconnection strategy for SSE

A stream that drops must resume, not restart — and a tab must only ever hold one of them.

What makes replay safe

  • Events carry absolute state. {"seconds": 41}, never {"seconds_delta": 3}. Applying an event twice is a no-op, which is what allows at-least-once delivery to be acceptable at all.
  • The client tracks its own cursor. A reconnect builds a new EventSource, and the browser will not resend Last-Event-ID for you across a new object — so the cursor is kept in a ref and sent as a query parameter.
  • Tickets are 60 seconds. Every reconnect fetches a fresh one before opening the stream. Reusing the expired ticket is the most obvious way to get this wrong.
  • Slow consumers are dropped, not buffered. A 100-event queue per subscriber; on overflow the connection closes with stream_overrun and the client reconnects and replays. Backpressure never reaches the session runner.
  • Heartbeat every 15 s as an SSE comment, which stops proxies and mobile radios from quietly killing an idle stream.
  • A first connection is not a reconnection. The room stream replays its ring to a new subscriber, because the discussion so far is exactly what a late joiner needs. The lobby stream does not: it opens from now, and only a real Last-Event-ID makes it replay.
Found by the browser test, and it was not a test bug. Replay was originally unconditional: replay_since(topics, 0) for anyone with no cursor. On the room stream that is right. On the lobby stream it meant that merely signing in re-delivered up to two hundred old events — and because the client turns session.ready into a live Join the discussion button, a user who opened the app was shown a way into a discussion that had ended the day before. The symptom that exposed it was subtler: a replayed session.ready arriving after a genuine new invitation.sent suppressed the invitation notification entirely, so the newest event on the stream was the one the user never saw. The fix is one flag and a comment about why the two streams differ — the lobby's state is loaded over REST when the page mounts, so replaying it is pure duplication; the room's state exists only in the stream.
One stream per tab — a limit that bites earlier than expected. The first implementation opened two streams per tab: a lobby stream in the shell and a room stream in the discussion page. Browsers allow six concurrent HTTP/1.1 connections per origin, shared across tabs of the same site, and idle keep-alive sockets count. With a few tabs open, the budget was gone and ordinary requests — including the one that submits your turn — queued behind the streams and never went out. The fix was structural rather than a tuning knob: the tab owns exactly one EventSource, and simply points it at a different endpoint depending on where the user is. The room endpoint already carries the user's own topic as well as the session's, so nothing was lost. In production, terminating HTTP/2 at nginx removes the limit entirely; the single-stream design is what makes the app correct on HTTP/1.1 anyway.

24Session cleanup

Two mechanisms: a finally block that always runs, and a janitor that sweeps whatever escaped it.

A cleanup bug the smoke test found twice. left_at IS NULL on session_participants is what enforces "one live discussion per person" — a partial unique index. But only the normal end-of-session path was setting left_at. A session that was provisioned and never joined therefore held its four participants out of every future classroom, permanently. It showed up as a correct-but-baffling 409 on the second test run. The same episode produced a smaller improvement worth keeping: provisioning now checks for busy participants up front and raises a 409 that names the problem, instead of letting the database's unique index surface as a 500.

25Scalability strategy

Scale by adding nodes and pinning each discussion to one of them. Nothing is shared except PostgreSQL.

The whole design rests on one property: a live session is confined to a single process. That is what removes the shared cache, the message broker and the distributed lock. It costs one thing — a node failure ends the discussions on that node — and for a twenty-minute conversation that is an acceptable trade, especially since the alternative machinery has failure modes of its own.

Generating a base frame once and scaling it with a C-speed operation fixed it, and the voice plane now skips synthesis entirely when no peer is on the media plane. Any per-sample loop in the audio path is a load-bearing performance decision, not a detail.

27Deployment architecture

Managed PostgreSQL, a small fleet of identical app nodes, a TURN server, and nothing else to operate.

Draining, not killing

A rolling deploy that SIGKILLs a node ends every discussion on it. The lifespan handler therefore drains: /readyz starts returning false so the balancer stops sending new sessions, then the orchestrator asks every live runner to close — each one speaks its closing remark, flushes its transcript and saves its summary — and only then does the process exit. The shutdown budget is 25 seconds, which comfortably covers a closing line and two database writes.

Four seats, but only two are required. A classroom offers four seats; a discussion runs on MIN_PARTICIPANTS_TO_START, which is two — you need somebody to disagree with, and that is the only real floor. The room opens by itself once nobody is still deciding, and the host may start earlier without waiting for a holdout. The old rule was "all four accepted, or nothing", which let one person who never opened the app hold three others hostage until the invitation expired. Starting early revokes the outstanding invitations, because a seat accepted after provisioning would belong to a session that was never built with it.
The rule that keeps the two honest. With in-app delivery, ensure_invitees() refuses an address that has no account rather than creating a passwordless row for it. That row would be an account with no way in: no password, and no emailed token either, because email is off. The seat would be held permanently by somebody who cannot reach it. For the same reason the host's picker excludes passwordless accounts — they exist only in the email model, and offering one would let a host fill a classroom with people who can never accept.

Delivery is a first-class state, not a log line. invitations.email_sent_at and email_error are written by the mail dispatcher after the send attempt and rendered on the host's roster. Without them, a seat that never fills has two indistinguishable explanations — nobody answered, or nobody was ever told — and only one of them is the host's to fix. 31API response format

One envelope for success, one for failure. A client writes one unwrapping function and one error handler, once.

// success — 200 / 201
{
  "data": { "id": "01a03d…", "title": "RAG — group discussion", "status": "INVITING" },
  "meta": {}
}

// paginated — keyset, never OFFSET
{
  "data": [ … ],
  "meta": { "next_cursor": "2026-08-26T09:14:02.113Z", "has_more": true }
}

// failure — any 4xx or 5xx, including ones nobody predicted
{
  "error": {
    "code": "classroom_not_ready",
    "message": "3 of 4 participants have accepted so far.",
    "details": { "accepted": 3, "required": 4 },
    "trace_id": "e13c56537ca74cbf"
  }
}
FieldContract
codeStable, machine-readable, never localised. Clients branch on this and nothing else.
messageWritten for a person, in the second person, saying what to do about it. Never a stack trace in production.
detailsStructured context — which fields failed, which provider is down, which users are busy.
trace_idThe request id, also returned as X-Request-ID and present on every log line for that request.
Conventions that go with it
  • Resource-shaped where it is CRUD, verb-shaped where it is a transition. POST /classrooms/{id}/start says what it does; PATCH {"status":"LIVE"} makes the client responsible for knowing the state machine.
  • 202 Accepted means the command was queued, not completed. Ending a discussion, releasing the floor and submitting a turn all return 202 — the outcome arrives over SSE, because that is where the room's truth lives.
  • Keyset pagination. ?cursor=<created_at>&limit=. Stable under concurrent inserts, unlike OFFSET.
  • Idempotency keys on the mutations that matter. Creating a classroom and accepting an invitation both accept an Idempotency-Key, because a double-tap on a flaky connection should not invite eight people.
  • 404 for "does not exist", 403 for "not yours". Once a caller has proven who they are, pretending a resource is missing tells them less and confuses them more.

Context, bound once

One filter pulls a whole discussion out of a busy node; another pulls one request out of a whole discussion.

What to alert on

circuit.open (a provider is down), runner.queue_full (the loop is behind), sse.overrun rate (clients cannot keep up), janitor.session_recovered (a node died with sessions on it), and unhandled_exception at any rate above zero. Everything else is a dashboard, not a page.

33Testing strategy

Four layers, each catching what the one below it structurally cannot.

What makes layers 1 and 2 possible

Three seams, and nothing else: the AI providers are Protocols with offline implementations; the voice plane is replaced by a fake that records what the runner asked for; and persistence is a Protocol with a list-backed double. A whole discussion — intro, rules, four turns, a follow-up, a disconnection, the closing remark, the summary and the wipe — runs in under a second with no database, no network and no audio device.

# tests/test_runner.py — the shape of every moderator test
async def test_a_thin_answer_earns_a_follow_up_before_the_floor_moves(...):

The browser test earns its cost. It runs five separate Chromium instances — not five contexts, because contexts of one browser share a socket pool and the test would then measure the harness rather than the product. It asserts on what a person sees: that the invitation appears without a reload, that the host's open page flips to READY from the event stream alone, that only the host is offered the End control, that the transcript accumulates, and that the summary renders. The load-bearing decision, restated. Everything above follows from one thing: a live discussion is confined to a single process, and only durable business facts leave it. That is what removes the broker, the cache and the distributed lock; it is what makes the moderator a testable pure function; and it is what makes "delete all conversation state when the session ends" a property of the design rather than a cleanup job that someone has to remember to run.
